# Интеллектуальное автозаполнение инцидентов поломок локомотивов (ОАО «НИИАС»)

Проект представляет собой асинхронный оркестратор на базе Spring Boot, интегрированный с веб-интерфейсом на React и аналитическим Python-конвейером на базе FastAPI для автоматического извлечения структурированных данных из сканированных и цифровых протоколов поломок локомотивов.

---

## 1. Архитектура системы и порты

Система разворачивается в изолированном Docker-окружении и состоит из **4 основных контейнеров**, объединенных в единую сеть `locomotive_network`. СУБД PostgreSQL может запускаться как внутри Docker-сети, так и на хост-машине.

| Контейнер | Название сервиса в Compose | Порт на хосте | Внутренний порт | Роль в системе |
| :--- | :--- | :--- | :--- | :--- |
| **Frontend** | `locomotive_frontend` | `80` (HTTP) | `80` | Раздача статики React через веб-сервер Nginx + Reverse Proxy запросов `/api/` |
| **Backend** | `locomotive_backend` | `8120` | `8080` | Оркестратор на Spring Boot (Java 21, асинхронные потоки) |
| **Database** | `locomotive_postgres` | `5432` | `5432` | СУБД PostgreSQL 16 (хранение BYTEA, JSONB и Flyway-миграции) |
| **FastAPI** | `fastapi-server` | `8045` | `8045` | Аналитический модуль на Python 3.11 (инференс моделей OCR и LLM Qwen) |

## 2. Три режима работы FastAPI

Вычисления ИИ-конвейера полностью перенесены внутрь контейнера `fastapi-server` (библиотека PyTorch). Режим работы и ресурсоемкость гибко настраиваются в блоке `environment` сервиса `fastapi` в файле `compose.yaml`:

### Режим А. Диагностический / Моковый (`MOCK_MODE=true`)
* **Суть:** Тяжелые модели не загружаются в память. При отправке файлов сервис мгновенно возвращает готовые статические ответы-заглушки.
* **Потребление ресурсов:** Минимальное (~100 МБ RAM). Подходит для тестирования интеграции на слабых ПК.

### Режим Б. Быстрый цифровой / Смарт-PDF (`MOCK_MODE=false`, `USE_OCR=false`)
* **Суть:** Используется для распознавания печатных цифровых PDF (где текст выделяется курсором). Библиотека `PyMuPDF` быстро вынимает текст в Markdown, а модель Qwen структурирует его в JSON. Визуальный OCR отключен.
* **Потребление ресурсов:** Среднее. Требуется память только под текстовую модель Qwen (~5-15 ГБ RAM в зависимости от размера модели).

### Режим В. Полнофункциональный ИИ (`MOCK_MODE=false`, `USE_OCR=true`)
* **Суть:** Работает с любыми файлами, включая сканы и фото документов. Визуальный OCR (Qianfan-OCR) считывает текст по картинке, а Qwen собирает из него итоговый JSON.
* **Потребление ресурсов:** Максимальное. В память загружаются обе нейросети (~20–25 ГБ RAM на CPU или ~18-22 ГБ VRAM на GPU).

## 3. Ключевые переменные окружения FastAPI

Управление параметрами ИИ осуществляется в `compose.yaml` без пересборки кода:

* `MOCK_MODE`: `true` (заглушки) / `false` (реальный ИИ).
* `USE_OCR`: `true` (включить Qianfan-OCR) / `false` (отключить OCR, только быстрый парсинг PDF).
* `DEVICE`: `cpu` / `cuda` — устройство вычислений для модели OCR.
* `TEXT_DEVICE`: `cpu` / `cuda` — устройство вычислений для текстовой модели Qwen.
* `TEXT_MODEL_NAME`: имя загружаемой модели Qwen (например, `Qwen/Qwen2.5-3B-Instruct` для CPU или `Qwen/Qwen2.5-7B-Instruct` для GPU).
* `MODEL_NAME`: локальный путь к весам OCR внутри контейнера (`/app/qianfan_ocr_flat`).

## 4. Важные технические фичи системы

### Умный фолбэк (Fallback) эндпоинтов `/ocr` и `/process`
Если бэкенд на Java отправляет запросы на стандартные эндпоинты `/ocr`, а в конфигурации установлено `USE_OCR=false`, FastAPI автоматически перехватывает файлы и обрабатывает их по быстрому гибридному пути (PyMuPDF + Qwen), не выдавая ошибок. Перенастройка бэкенда при этом не требуется.

### Детекция дубликатов на основе перцептивного хэша (pHash)
При обработке первой страницы документа вычисляется его визуальный хэш. Бэкенд Java сравнивает его с хэшами документов за последние 30 дней по алгоритму Хэмминга. При расстоянии менее 8 бит документ признается дубликатом. Информация о дубликате (оригинальный инцидент, имя файла, дата обработки и ранее распознанные поля) записывается в формате JSON в отдельную колонку `duplicate_details` в БД.

## 5. Панель разработчика (Developer Tools Dashboard)

Доступна по адресу: `http://localhost/developer` (или по кнопке «🛠️ Панель разработчика» в шапке). 

Представляет собой интерактивную песочницу для отладки:
* **Прямая отправка:** возможность отправить любой документ напрямую в обход бэкенда и БД.
* **Интерактивные окна:** окна вывода сырого Markdown, готового JSON и системных логов можно перетаскивать, растягивать и масштабировать (шрифт) под разрешение вашего экрана.
* **Автосохранение:** все логи, истории запусков и выводы сохраняются в `LocalStorage` браузера и не пропадают при перезагрузке страницы (`F5`).

## 6. Требования к системным ресурсам

Рекомендуемые системные характеристики хост-машины при работе реальных моделей в боевом режиме (`MOCK_MODE=false`):

### При работе на CPU (Процессор)
* **Оперативная память (RAM):**
  * При использовании `Qwen2.5-3B-Instruct` + `USE_OCR=false`: **не менее 16 ГБ RAM**.
  * При использовании `Qwen2.5-7B-Instruct` + `USE_OCR=true`: **не менее 32 ГБ RAM**.
* **Процессор:** не менее 6–8 физических ядер (например, Ryzen 5 5600, Intel i5-12400) с поддержкой инструкций AVX2.

### При работе на GPU (Видеокарта NVIDIA)
* **Видеопамять (VRAM):**
  * При использовании `Qwen2.5-3B-Instruct`: не менее **8 ГБ VRAM** (RTX 3070 / 4060).
  * При использовании `Qwen2.5-7B-Instruct`: не менее **16–24 ГБ VRAM** (RTX 3090 / 4090 / A10 / A100).
* Требуется установленный NVIDIA Container Toolkit на хосте.

## 7. Быстрый запуск проекта через Docker Compose

### Сборка и запуск всей системы в фоновом режиме:
docker compose up -d --build

### Полная остановка системы с очисткой контейнеров:
docker compose down

### Мониторинг логов всех контейнеров в реальном времени с таймштампами:
docker compose logs -f -t

## 8. Офлайн-развертывание на закрытом сервере (Air-Gapped)

### Шаг А (На компьютере разработчиков с интернетом)
1. Соберите все образы системы локально:
   docker compose build
2. Экспортируйте образы в tar-архивы:
   docker save -o postgres.tar postgres:16-alpine
   docker save -o backend.tar locomotive_backend:latest
   docker save -o fastapi.tar fastapi-server:latest
   docker save -o frontend.tar locomotive_frontend:latest
3. Скопируйте файлы архивов, корневой файл `compose.yaml` и папку локальных весов `qianfan_ocr_flat` на защищенный внешний накопитель.

### Шаг Б (На закрытом сервере)
1. Импортируйте образы в локальный Docker:
   docker load -i postgres.tar
   docker load -i backend.tar
   docker load -i fastapi.tar
   docker load -i frontend.tar
2. Запустите систему из папки с файлом `compose.yaml` и папкой весов `qianfan_ocr_flat`:
   docker compose up -d
